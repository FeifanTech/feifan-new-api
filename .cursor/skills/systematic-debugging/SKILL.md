# 系统化调试 Skill

## 触发条件

- 用户报告 Bug、测试失败、线上故障、异常行为。
- 用户提到：调试、排查、根因、故障、异常、报错。

## 核心原则

- 不急于修，先理解**根因**；修要**多层防御**；修完要**验证**；最后**沉淀**到 memory/ 或 Skill。
- 与 AI-DLC 一致：若任务带 **Level 1 Plan**，可将本 Skill 作为「故障/Bug 类 Intent」对应的 Stage；**Human Gate**（如发布前、变更生产）须由人确认。

---

## 四阶段流程

### 阶段 1：根因追踪（Root Cause Tracing）

**目标**：找到真正的根本原因，而不是表面现象。

**步骤**：

1. **收集症状**：错误信息、复现步骤、日志、监控数据。
2. **5-Why 或等价分析**：从现象逐层追问「为什么」，直到可行动根因（如代码未关闭连接、配置错误、依赖版本不兼容）。
3. **时间线重建**（若适用）：关键事件顺序，便于与监控/日志对齐。
4. **假设验证**：提出可验证的假设（如「若是 X，则 Y 应成立」），用日志/复现/监控验证。

**产出**：简短根因结论（一句话）+ 支撑证据；可选写入 memory/ 或 decisions（Proposed，待人确认）。

---

### 阶段 2：多层防御（Defense in Depth）

**目标**：不只修一个点，而是建立预防、检测、缓解、恢复的层次。

**层次**：

1. **预防层**：从源头避免（如更新编码规范 Skill、静态规则、依赖版本）。
2. **检测层**：尽早发现（监控告警、单测/集成测覆盖）。
3. **缓解层**：减轻影响（限流、超时、降级、配置调优）。
4. **恢复层**：快速恢复（回滚、重启、数据修复流程）。

**产出**：针对当前根因的 1～4 层措施建议；若涉及规范或 Skill 更新，标注「待写入 memory/ 或 Skill」。

---

### 阶段 3：修复验证（Verification Before Completion）

**目标**：确保修复真正有效，不引入新问题。

**步骤**：

1. **修复代码/配置**：按根因与多层防御方案实施。
2. **单元/集成测试**：覆盖改动路径与回归范围。
3. **复现验证**：按原复现步骤验证问题消失。
4. **灰度/分批**（若涉及生产）：小流量观察再全量。
5. **监控确认**：关键指标与告警恢复正常。

**产出**：修复说明 + 验证结论；若为生产变更，须经 **Human Gate**（如 TL 或指定人）确认后再全量。

---

### 阶段 4：经验沉淀（Memory Update）

**目标**：将教训转化为可追溯、可复用的记忆与预防机制。

**步骤**：

1. **记录**：将故障/根因/措施摘要写入 **memory/**（如 `memory/decisions.md` Proposed 或 `memory/changelog.md`）；若有独立故障复盘，可放在 `memory/` 下约定路径（如 `memory/incidents/`，若团队已约定）。
2. **更新 Skill**（若适用）：若根因与编码/架构/运维规范相关，在对应 Skill 中补充检查项或红旗（并注明来源，如「来源：memory/incidents/YYYY-MM-xxx」）。
3. **与 Plan 可追溯**：若本次调试对应某 Level 1 Plan，在 Commit/PR 或决策记录中引用 Plan-ID。

**产出**：memory/ 更新摘要；若有 Skill 变更，见 changelog 或对应 SKILL.md。

---

## 调试反模式（禁止）

- ❌ **急于修复**：未完成阶段 1（根因追踪）就改代码。
- ❌ **单点修复**：只改一处，无预防/检测/缓解/恢复考虑。
- ❌ **修复未验证**：未通过测试或复现验证即视为完成。
- ❌ **经验流失**：修复后不写入 memory/ 或不更新相关 Skill。

触达上述任一条即应回到对应阶段补全，不自行合理化绕过。

---

## 与 memory/ 的联动

- 若当前仓库存在 `memory/` 目录：
  - 根因结论与措施可写入 `memory/decisions.md` 的 **Proposed** 区（待人确认后移至 Accepted）。
  - 故障摘要与复盘可写入 `memory/changelog.md` 或团队约定的 incidents 路径。
  - 若更新了 Skill，在 `memory/changelog.md` 中记录：日期、更新了哪个 Skill、主要变更点。
- 若不存在 `memory/`，则跳过写入，不报错；仍须完成四阶段逻辑。

---

## 工作结束后的默认动作

- **提交 GitHub**：修复与文档/ memory 更新完成后，建议用户执行提交；commit 信息需清晰、可与故障/Plan 关联。
- 若本次更新了 Skill 或 memory/，建议 commit 信息含 `chore(skills): …` 或 `docs(memory): …`。

---

## 使用说明

- 与 **using-skills** 配合：当用户报告 Bug/故障时，using-skills 会加载本 Skill。
- 与 **code-standards** / **architecture-principles** 配合：若根因涉及规范缺失，可在对应 Skill 中补充检查项或红旗。
- 与 AI-DLC 一致：故障类任务可在 Level 1 Plan 中标注「使用 systematic-debugging」；Human Gate 处由人确认发布或变更。
