# 设计评审检查清单

## 触发条件

- 用户提到：设计评审、架构评审、审查技术方案、design review、方案评审。
- 用户意图：对已有设计/技术方案文档做逐条审查并给出结论。

## 执行前说明

本 Skill 依据《技术架构原则》的评审检查清单，对设计文档逐条给出「满足/不满足/待补充」及简短说明；每条检查项必须给出结论。

## 检查清单（与 architecture-principles 对齐）

- [ ] **背景与约束**：方案是否写清背景、目标及约束（性能、可用性、合规）？
- [ ] **职责与边界**：核心组件/服务职责是否单一？边界是否明确、依赖方向是否清晰、无循环依赖？
- [ ] **依赖与调用链**：依赖关系与调用链是否画出或列出？是否标注数据流向？
- [ ] **技术选型**：选型理由是否充分？是否有替代方案对比或说明不选理由？
- [ ] **接口/契约**：接口或契约是否稳定？版本策略（兼容、废弃）是否明确？
- [ ] **可观测性**：日志、监控、告警是否覆盖关键路径？是否便于排障与容量规划？
- [ ] **风险与回滚**：是否列出主要风险与回滚/降级策略？

## 产出格式

- 逐条对照上述检查项，标明「满足/不满足/待补充」及 1～2 句说明。
- 输出时每条检查项必须给出结论，避免只列清单不判断。
- 可与 **role-architect** 或 **architecture-principles** 串联使用。

## 企业级检查清单（可选，按技术栈择一）

- 若项目技术栈为 **Java/Spring**，请结合 `docs/architecture/JAVA_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论。
- 若项目技术栈为 **Python/FastAPI 或 Django**，请结合 `docs/architecture/PYTHON_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论。
- 若项目技术栈为 **TypeScript/Node/Nest**，请结合 `docs/architecture/TS_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论。
- 每个维度必须给出结论，不能只罗列问题；非上述技术栈可跳过本段。

## 与 memory/ 的联动（可选）

- 若当前仓库存在 `memory/` 目录，且本次产出了**架构/设计决策**（选型、接口约定、权衡结论），则在输出评审结论后，将决策摘要追加到 `memory/decisions.md` 的 **Proposed** 区（ADR 风格：背景、约束、方案、结论）；待人工确认后再移至 Accepted。
- 若本轮任务或会话结束，可将本次摘要追加到 `memory/changelog.md`：日期、本次做了什么、涉及文档或模块、如何验证。
- 若不存在 `memory/`，则跳过本段，不报错。

## 使用说明

- 用户可说「按设计评审清单审查这份技术方案」「做一轮架构评审」。
- 完整原则与产出物建议见 `.cursor/skills/architecture-principles/SKILL.md`。
