# 技术架构原则

## 触发条件

- 用户提到：架构设计、技术方案、技术选型、系统设计、接口设计、ADR、架构评审。
- 用户意图：撰写或评审技术方案/架构文档、希望按架构原则做检查。

## 红旗清单（触达即停，交人决策）

以下为可观察的违规行为；任一条触达须停止，将决策交给人，不自行合理化绕过。

1. **Controller/接口层直接依赖 Mapper/DAO/Repository 实现类**  
   常见借口：「简单 CRUD 不需要分层」「这样更直接」「减少抽象」。→ 触达即停，交人决策。

2. **实体/领域对象为贫血模型（仅有 getter/setter，无业务方法）**  
   常见借口：「业务逻辑在 Service 统一管理」「这样更简单」。→ 触达即停，交人决策。

3. **跨层直接调用（如表现层直调数据层、跨限界上下文无接口）**  
   常见借口：「读操作不需要完整分层」「只是查一下」。→ 触达即停，交人决策。

4. **核心组件无职责边界或限界上下文未明确**  
   常见借口：「先实现再说」「边界后面再划」。→ 触达即停，交人决策。

5. **方案中未考虑可观测性、安全或合规（关键路径无日志/指标/鉴权等）**  
   常见借口：「先跑通功能」「安全后面加」。→ 触达即停，交人决策。

## 核心原则（请按团队实际替换）

1. **简单优于复杂**：在满足需求的前提下优先简单方案，避免过度设计。
2. **边界清晰**：模块/服务职责单一，依赖方向明确，避免循环依赖。
3. **可观测**：关键路径有日志、指标或追踪，便于排障与容量规划。
4. **可演进**：预留扩展点或兼容策略，避免一次性大爆炸式改造。
5. **安全与合规**：数据与接口符合安全与合规要求（认证、鉴权、敏感数据脱敏等）。

## 评审检查清单

- [ ] **背景与约束**：方案是否写清背景、目标及约束（性能、可用性、合规）？
- [ ] **职责与边界**：核心组件/服务职责是否单一？边界是否明确、依赖方向是否清晰、无循环依赖？
- [ ] **依赖与调用链**：依赖关系与调用链是否画出或列出？是否标注数据流向？
- [ ] **技术选型**：选型理由是否充分？是否有替代方案对比或说明不选理由？
- [ ] **接口/契约**：接口或契约是否稳定？版本策略（兼容、废弃）是否明确？
- [ ] **可观测性**：日志、监控、告警是否覆盖关键路径？是否便于排障与容量规划？
- [ ] **风险与回滚**：是否列出主要风险与回滚/降级策略？

## 产出物建议

- **技术方案**：背景、目标、架构图、核心模块说明、接口与数据流、选型理由、风险与回滚。
- **ADR**：背景、决策、后果；可放在 `references/adr-templates.md` 供引用。
- **评审结论**：逐条对照上述检查项，标明「满足/不满足/待补充」及简短说明；每条检查项必须给出结论。（参考市场：输出明确、可核对）

## 企业级检查清单（可选，按技术栈择一）

- 若项目技术栈为 **Java/Spring**，请结合 `docs/architecture/JAVA_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论（满足/不满足/风险 + 建议）。
- 若项目技术栈为 **Python/FastAPI 或 Django**，请结合 `docs/architecture/PYTHON_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论。
- 若项目技术栈为 **TypeScript/Node/Nest**，请结合 `docs/architecture/TS_ENTERPRISE_CHECKLIST.md` 第一、架构设计检查清单（1.1～1.7），逐项审查并给出结论。
- 每个维度必须给出结论，不能只罗列问题；非上述技术栈可跳过本段。

## 与 memory/ 的联动（可选）

- 若当前仓库存在 `memory/` 目录，且本次产出了**架构/设计决策**（选型、接口约定、权衡结论、ADR），则在输出评审结论或技术方案后，将决策摘要追加到 `memory/decisions.md` 的 **Proposed** 区（ADR 风格：背景、约束、方案、结论）；待人工确认后再移至 Accepted。
- 若本轮任务或会话结束，可将本次摘要追加到 `memory/changelog.md`：日期、本次做了什么、涉及模块、如何验证。
- 若不存在 `memory/`，则跳过本段，不报错。

## 工作结束后的默认动作

- **提交 GitHub**：任务或迭代完成后，默认执行或明确建议用户执行「提交到 GitHub」（`git add` → `git commit` → `git push`），避免工作结束未提交导致无法回滚；commit 信息需清晰、可与需求/任务关联。

## 使用说明

- 本 Skill 可被 **role-architect** 引用：角色 Agent 先遵循本原则与检查清单，再按任务产出技术方案或评审结论。
- 单独做技术方案/架构评审时，Agent 可直接匹配本 Skill；写技术方案或 ADR 时建议与 role-architect 串联使用。
