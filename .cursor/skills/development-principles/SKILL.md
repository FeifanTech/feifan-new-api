# 开发原则

## 红旗清单（触达即停，交人决策）

以下为可观察的违规行为；任一条触达须停止，将决策交给人，不自行合理化绕过。

1. **在写测试之前就写了实现代码（违反 TDD/测试先行）**  
   常见借口：「测试稍后补」「先实现再测」。→ 触达即停，交人决策。

2. **未经 Code Review 或指定人确认就合并到 main/主分支**  
   常见借口：「小改动」「很急」。→ 触达即停，交人决策。

3. **产出了架构/接口/决策类结论但未写入 memory/ 或约定文档**  
   常见借口：「口头说过」「后面补文档」。→ 触达即停，交人决策。

4. **以「这次可跳过」为由跳过检查清单且无人明确批准**  
   常见借口：「情况特殊」「理解精神」。→ 触达即停，交人决策。

5. **交付物与 Plan/需求范围明显不一致且未经过人确认变更**  
   常见借口：「顺带做了」「范围 creep 可接受」。→ 触达即停，交人决策。

## 核心原则（请按团队实际替换）

1. **小步交付**：可独立交付的小步迭代，每步可验证、可回滚，避免大爆炸发布。
2. **质量门禁**：提交前自检、Code Review、关键路径有测试或可验证方式，不把问题留到下阶段。
3. **可追溯**：需求/任务与代码、提交、发布可关联，便于排查与复盘。
4. **协作一致**：分支与发布策略、接口契约、文档与团队约定保持一致。
5. **持续改进**：定期回顾交付节奏与质量数据，调整实践与规范。

## 开发过程检查清单

- [ ] 本迭代/任务目标是否清晰、可验收？
- [ ] 是否按小步提交、便于回滚与追溯？
- [ ] 提交前是否完成自检（含 code-standards 要点）？
- [ ] 关键逻辑是否有测试或可验证方式？
- [ ] 接口/契约变更是否与调用方对齐、有文档或版本说明？
- [ ] 是否有不必要的阻塞依赖或等待？

## 企业级检查清单（可选，按技术栈择一）

- 若项目为 **Java 企业级应用**，请结合 `docs/architecture/JAVA_ENTERPRISE_CHECKLIST.md` 第二、编码与实现检查清单（2.1～2.8）自检，并给出结论与建议。
- 若项目为 **Python 企业级应用**，请结合 `docs/architecture/PYTHON_ENTERPRISE_CHECKLIST.md` 第二、编码与实现检查清单（2.1～2.8）自检，并给出结论与建议。
- 若项目为 **TypeScript/Node 企业级应用**，请结合 `docs/architecture/TS_ENTERPRISE_CHECKLIST.md` 第二、编码与实现检查清单（2.1～2.8）自检，并给出结论与建议。
- 非上述技术栈可跳过本段。

## 产出物建议

- **迭代/任务**：目标、验收标准、依赖与风险、完成后的回顾要点。
- **提交**：清晰的 commit 信息、与需求/任务关联（如 issue 编号）。

## 与 memory/ 的联动（可选）

- 若当前仓库存在 `memory/` 目录，且本次产出了**迭代/任务约定或分支与发布策略**，则可追加到 `memory/engineering.md` 的约定区。
- 若本轮任务或会话结束，可将本次摘要追加到 `memory/changelog.md`：日期、本次做了什么、涉及模块或任务、如何验证。
- 若不存在 `memory/`，则跳过本段，不报错。

## 工作结束后的默认动作

- **提交 GitHub**：任务或迭代完成后，默认执行或明确建议用户执行「提交到 GitHub」（`git add` → `git commit` → `git push`），避免工作结束未提交导致无法回滚；commit 信息需清晰、可与需求/任务关联。

## 使用说明

本 Skill 可被「开发者的角色」引用；也可在讨论开发流程、交付质量时由 Agent 自动匹配。与 `code-standards` 配合：开发原则偏过程与质量门禁，代码规范偏代码层面。
