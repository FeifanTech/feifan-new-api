# 产品设计原则

## 触发条件

- 用户提到：写 PRD、需求评审、PRD 评审、功能设计、用户故事、体验设计、产品方案。
- 用户意图：撰写或评审需求类文档、希望按产品设计原则做检查。

## 红旗清单（触达即停，交人决策）

以下为可观察的违规行为；任一条触达须停止，将决策交给人，不自行合理化绕过。

1. **在未形成 PRD/范围或需求摘要的情况下进入详细设计或实现**  
   常见借口：「需求很清楚」「先做再补文档」。→ 触达即停，交人决策。

2. **验收标准不可测或不可验收（模糊表述、无明确完成条件）**  
   常见借口：「大家理解一致」「上线再看」。→ 触达即停，交人决策。

3. **关键假设或决策未记录在 PRD/memory/ 或决策文档中**  
   常见借口：「会上说过」「口头约定」。→ 触达即停，交人决策。

4. **未考虑边界与异常场景（空值、失败、超时、权限等）**  
   常见借口：「主流程先做」「异常后面补」。→ 触达即停，交人决策。

5. **需求变更未回溯到 PRD 或未在可追溯处记录**  
   常见借口：「小调整」「不影响文档」。→ 触达即停，交人决策。

## 核心原则（请按团队实际替换）

1. **用户与场景先行**：每个功能明确目标用户与使用场景，避免「所有人」。
2. **目标可衡量**：产品目标可拆解为可观测的指标或验收标准。
3. **优先级清晰**：需求有 P0/P1/P2 或等价分级，并说明理由。
4. **闭环与反馈**：关键操作有结果反馈与可追溯路径。
5. **一致性**：交互、术语、视觉与既有产品/规范一致。

## 评审检查清单

- [ ] **背景与目标**：文档是否包含「背景」「目标」两节？目标是否可量化（指标或验收标准）？
- [ ] **用户与场景**：是否明确目标用户与至少一个典型使用场景？是否避免「所有人」？
- [ ] **功能与优先级**：功能列表是否完整、无歧义？是否标注 P0/P1/P2 或等价优先级及理由？
- [ ] **非功能需求**：性能、安全、合规是否提及？若有，是否可验证？
- [ ] **成功指标**：成功指标或验收标准是否可执行（可测量、可验收）？
- [ ] **一致性**：交互、术语、视觉是否与现有产品/设计规范一致？

## 产出物建议结构

- **PRD**：背景、目标、用户与场景、功能列表（含优先级）、非功能需求、成功指标。
- **评审结论**：逐条对照上述检查项，标明「满足/不满足/待补充」及简短说明；输出时每条检查项必须给出结论，避免只列清单不判断。（参考 Anthropic doc-coauthoring：输出明确、可核对）

## 与 memory/ 的联动（可选）

- 若当前仓库存在 `memory/` 目录，且本次产出了**产品范围、用户画像、成功指标或 PRD 定稿摘要**，则在输出后，将摘要追加到 `memory/product.md` 的 **Proposed** 区（或约定区）；待人工确认后再视为已采纳。
- 若本轮任务或会话结束，可将本次摘要追加到 `memory/changelog.md`：日期、本次做了什么、涉及文档或模块、如何验证。
- 若不存在 `memory/`，则跳过本段，不报错。

## 工作结束后的默认动作

- **提交 GitHub**：任务或迭代完成后，默认执行或明确建议用户执行「提交到 GitHub」（`git add` → `git commit` → `git push`），避免工作结束未提交导致无法回滚；commit 信息需清晰、可与需求/任务关联。

## 使用说明

- 本 Skill 可被 **role-product-designer** 引用：角色 Agent 先遵循本原则与检查清单，再按任务产出 PRD 或评审结论。
- 单独做需求/PRD 评审时，Agent 可直接匹配本 Skill；写 PRD 时建议与 role-product-designer 串联使用。
